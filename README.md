## 🌟 مشخصات و معماری فنی (Tech Stack)

این سیستم بر پایه مدرن‌ترین معماری وب طراحی و پیاده‌سازی شده است:

- **هسته و فریم‌ورک:** Next.js 15 (App Router) + React 19
- **زبان:** TypeScript (Type-Safe Architecture)
- **پایگاه داده و مدل‌سازی:** MongoDB Atlas + Mongoose ORM
- **طراحی و استایلینگ:** Tailwind CSS (طراحی اختصاصی Luxury Dark & Amber/Gold)
- **احراز هویت و امنیت:** Custom JWT Auth + Bcrypt Password Hashing + Next.js Middleware Protection
- **امنیت API و پنل پیامکی:** Rate Limiting اختصاصی جهت جلوگیری از حملات Brute Force و محافظت از هزینه‌های SMS Gateway
- **مدیریت وضعیت (State Management):** React Context API (مدیریت سبد خرید و نشست‌های کاربری)
- **بهینه‌سازی رسانه‌ها و سرعت:** Next.js Image Optimization + کامپوننت‌های اسکلتون لودینگ (Skeleton Screens)

## ⚙️ راهنمای اجرا و راه‌اندازی (Getting Started)

### ۱. نصب وابستگی‌ها

```bash
npm install
```

### ۲. تنظیم متغیرهای محیطی (.env.local)

فایل `.env.local` را با مقادیر دیتابیس، سکرت JWT و کلیدهای سامانه پیامکی تنظیم کنید:

```env
MONGODB_URI=your_mongodb_connection_string
JWT_SECRET=your_jwt_secret_key
NEXT_PUBLIC_APP_URL=http://localhost:3000
```

برای فعال‌سازی پیامک بازیابی رمز، ریست رمز توسط مدیر ارشد، اعلان درخواست مشاوره و هشدار ورود مدیر ارشد، پس از تهیه سرویس وب‌سرویس از ملی‌پیامک این مقادیر را در `.env.local` (و در محیط استقرار، در Secretهای سرور) قرار دهید:

```env
MELIPAYAMAK_USERNAME=your_melipayamak_username
MELIPAYAMAK_PASSWORD=your_melipayamak_password
MELIPAYAMAK_FROM=your_authorized_sender_number
```

`MELIPAYAMAK_FROM` باید خط فرستنده‌ی فعال و مجاز حساب شما باشد. پس از افزودن مقادیر، سرور را دوباره اجرا کنید. اطلاعات ورود پیامک فقط در سرور استفاده می‌شوند و نباید با پیشوند `NEXT_PUBLIC_` تنظیم یا در مخزن ثبت شوند. اعتبار کد بازیابی در سرور ۱۰ دقیقه است.

### ۳. اجرای پروژه در محیط توسعه

```bash
npm run dev
```

### ۴. ساخت بیلد نهایی و اجرا در پروداکشن

```bash
npm run build
npm run start
```

## 📘 معماری و راهنمای نگهداری پروژه

این بخش ساختار واقعی پیاده‌سازی، جریان‌های اصلی داده و تغییرات پنل‌ها را توضیح می‌دهد تا توسعه و استقرار سامانه با شناخت دقیق‌تری انجام شود.

### ساختار کد

| مسیر          | مسئولیت                                                                               |
| ------------- | ------------------------------------------------------------------------------------- |
| `app/(store)` | صفحات عمومی سایت، ورود و ثبت‌نام، پنل کاربر و بخش‌های مرتبط با خرید دوره              |
| `app/admin`   | داشبورد و صفحات مدیریتی؛ صفحه‌ها و عملیات بر اساس نقش کاربر کنترل می‌شوند             |
| `app/api`     | Route Handlerهای احراز هویت، محتوا، مشاوره، دوره‌ها، سفارش‌ها، پرداخت و مدیریت        |
| `components`  | فرم‌ها، اجزای مشترک سایت و پنل، ناوبری، dialogها و اعلان‌ها                           |
| `context`     | وضعیت مشترک رابط کاربری، از جمله سبد خرید                                             |
| `models`      | Schemaهای Mongoose برای کاربران، سفارش‌ها، پرداخت، دوره، مقاله، مشاوره و سایر داده‌ها |
| `lib`         | اتصال MongoDB، نشست و نقش‌ها، اعتبارسنجی، درگاه‌ها، rate limit و منطق مشترک           |
| `data`        | داده‌های اولیه و ثابت موردنیاز بخش‌های سایت                                           |
| `public`      | تصاویر، فونت‌ها، فایل‌های عمومی و بارگذاری‌های سایت                                   |
| `scripts`     | اسکریپت‌های کمکی مانند آماده‌سازی مدیران اولیه                                        |

مسیرهای دارای پرانتز مانند `app/(store)` گروه‌بندی Next.js هستند و بخشی از URL مرورگر نمی‌شوند. Alias `@/` در کد به ریشه پروژه اشاره می‌کند.

### ورود و نقش‌های مدیریتی

- احراز هویت با JWT در cookie امن و HttpOnly انجام می‌شود؛ رمزهای عبور با `bcryptjs` هش می‌شوند.
- ورود به پنل بر اساس نقش هدایت می‌شود: مدیر ارشد به `/admin` و مدیر عادی به `/admin/manager` می‌رود. مسیر مدیر عادی با middleware به داشبورد مشترک role-aware بازنویسی می‌شود.
- middleware دسترسی مسیرهای مدیریتی را بررسی می‌کند؛ عملیات حساس نیز باید در Route Handler سمت سرور نقش را دوباره کنترل کنند. پنهان‌کردن دکمه در UI به‌تنهایی مرز امنیتی محسوب نمی‌شود.
- مدیر عادی در ناوبری پنل به بخش‌های اصلی مشاوره، ثبت‌نام دوره‌ها، مقالات و پروژه‌ها دسترسی دارد. مدیر ارشد علاوه بر آن‌ها بخش پرداخت‌ها، صندوق یادداشت‌ها، تنظیمات و مدیریت‌های اختصاصی خود را می‌بیند.
- در مقالات، مدیر عادی می‌تواند مقاله جدید را به شکل پیش‌نویس ذخیره و فهرست را مشاهده کند؛ انتشار، ویرایش و حذف برای مدیر ارشد است.
- در پروژه‌ها، مدیر عادی امکان ایجاد و ویرایش دارد؛ حذف و ارسال/همگام‌سازی با راه‌اندازی‌ها برای مدیر ارشد است. دکمه ارسال اولیه قرمز و دکمه به‌روزرسانی سبز نمایش داده می‌شود.
- صندوق یادداشت‌های مدیران فقط برای مدیر ارشد قابل مشاهده است. مدیران می‌توانند یادداشت داخلی روی درخواست مشاوره ثبت کنند؛ حذف یادداشت، درخواست اصلی را حذف نمی‌کند.

### جریان‌های اصلی سامانه

#### درخواست مشاوره

فرم سایت اطلاعات را به `POST /api/consultations` می‌فرستد. پس از اعتبارسنجی و ذخیره درخواست در MongoDB، خلاصه درخواست به شماره موبایل حساب مدیر ارشد پیامک می‌شود. ارسال اعلان بعد از پاسخ HTTP انجام می‌شود تا اختلال سرویس پیامک مانع ثبت درخواست نشود. برای کنترل هزینه SMS، ثبت عمومی درخواست به ۳ بار در ۱۰ دقیقه برای هر IP محدود است.

در پنل، مدیر وضعیت درخواست را به «بررسی‌شده» یا «ارجاع‌شده» تغییر می‌دهد و می‌تواند یادداشت داخلی ثبت کند. پیامک درخواست به شماره `mobile` مدیر ارشد در مجموعه کاربران می‌رود؛ این همان شماره‌ای است که در تنظیمات مدیر ارشد تغییر می‌کند.

#### پیامک و بازیابی رمز

- ارسال پیامک با وب‌سرویس HTTPS ملی‌پیامک و متد `SendSimpleSMS2` انجام می‌شود.
- کد بازیابی ۶ رقمی است، مقدار خام کد در پایگاه‌داده ذخیره نمی‌شود و فقط hash آن نگه‌داری می‌شود.
- انقضای ۱۰ دقیقه‌ای در سمت سرور هنگام تأیید کد و هنگام ذخیره رمز جدید بررسی می‌شود؛ کد در لحظه پایان مهلت نیز معتبر نیست.
- ارسال مجدد cooldown یک‌دقیقه‌ای، محدودیت تلاش کد و rate limit برای درخواست و تأیید کد دارد.
- در ریست رمز از پنل مدیر ارشد، پیامک رمز موقت باید موفق شود؛ در صورت نبود تنظیمات یا شکست ارسال، رمز حساب تغییر نمی‌کند.
- پس از ورود موفق از پنل ادمین توسط مدیر ارشد، هشدار ورود به شماره همان حساب ارسال می‌شود. ورود عادی به پنل کاربر این اعلان را فعال نمی‌کند.
- خطای پیامک درخواست مشاوره یا هشدار ورود، عملیات اصلی را شکست نمی‌دهد؛ خطا در log سرور ثبت می‌شود.

#### دوره‌ها و پرداخت

سفارش دوره‌ها و اقلام آن‌ها در `Order` و رکورد پرداخت در `Payment` نگه‌داری می‌شوند. برای پرداخت غیررایگان، سرور از زرین‌پال Authority می‌گیرد، کاربر را به درگاه هدایت می‌کند و callback وضعیت پرداخت را با سرویس verify بررسی می‌کند. فقط پس از تأیید درگاه، Payment موفق و Order پرداخت‌شده ثبت می‌شود.

در پنل مدیر ارشد، جدول پرداخت جزئیات دوره، تعداد، قیمت واحد، جمع اقلام، مبلغ کل، کاربر، سفارش، شناسه Authority و زمان را نشان می‌دهد. شمار و جمع مالی فقط از پرداخت‌های موفق با مبلغ مثبت و شناسه واقعی زرین‌پال محاسبه می‌شوند؛ رکوردهای رایگان یا شناسه‌های داخلی `PAY-...` درآمد واقعی درگاه محسوب نمی‌شوند.

#### داشبورد خدمات

داشبورد آمار آموزش، مشاوره و پروژه‌ها را بر اساس نقش ارائه می‌کند. مدیر ارشد علاوه بر این شاخص‌ها، راه‌اندازی‌ها، کاربران، یادداشت‌های صندوق و آمار پرداخت واقعی زرین‌پال را می‌بیند. پاسخ API داشبورد، شاخص‌های اختصاصی مدیر ارشد را برای مدیر عادی برنمی‌گرداند.

### متغیرهای محیطی

متغیرها را در `.env.local` برای توسعه و در Secretهای محیط استقرار برای production قرار دهید. فایل `.env*` در Git نادیده گرفته می‌شود؛ مقادیر واقعی و اطلاعات ورود را در README، کد یا چت قرار ندهید.

```env
MONGODB_URI=your_mongodb_connection_string
JWT_SECRET=replace_with_a_long_random_secret

# دامنه HTTPS اصلی؛ برای callback زرین‌پال در production تنظیم شود
NEXT_PUBLIC_SITE_URL=https://example.com

# زرین‌پال؛ مقدار Sandbox در تست true و در محیط عملیاتی false باشد
ZARINPAL_MERCHANT_ID=your_merchant_id
ZARINPAL_SANDBOX=true

# ملی‌پیامک؛ اطلاعات فقط در سرور نگه‌داری شوند
MELIPAYAMAK_USERNAME=your_melipayamak_username
MELIPAYAMAK_PASSWORD=your_melipayamak_password
MELIPAYAMAK_FROM=your_authorized_sender_number
```

`NEXT_PUBLIC_SITE_URL` برای callback پرداخت و URLهای canonical استفاده می‌شود؛ مقدار آن در production باید دامنه‌ی نهایی HTTPS باشد. برای فعال‌شدن پیامک، حساب ملی‌پیامک باید دسترسی وب‌سرویس داشته باشد و خط `MELIPAYAMAK_FROM` برای ارسال مجاز باشد. پس از تغییر متغیرهای محیطی، سرور را دوباره راه‌اندازی کنید. هیچ‌یک از این مقادیر نباید با پیشوند `NEXT_PUBLIC_` منتشر شود.

در محیط توسعه، اگر تنظیمات ملی‌پیامک خالی باشد، کد بازیابی برای تست محلی در log سرور نوشته می‌شود؛ در production، نبود تنظیمات به‌عنوان خطای ارسال پاسخ داده می‌شود.

### اعلان‌های رابط کاربری

اعلان‌های سایت از `ToastProvider` سراسری استفاده می‌کنند و جایگزین `alert()` و `confirm()` بومی مرورگر شده‌اند. اعلان‌ها قابل بستن و زمان‌دارند؛ در موبایل بالاتر از نوار ناوبری ثابت قرار می‌گیرند. تأیید عملیات مخرب و پرداخت بیعانه از dialog داخلی استفاده می‌کند.

### ملاحظات توسعه و استقرار

- Route Handlerها مرز اصلی اعتبارسنجی ورودی و مجوز عملیات هستند؛ در تغییرات نقش، هم UI و هم endpoint مربوطه باید بررسی شوند.
- `lib/rate-limit.ts` از حافظه‌ی همان process استفاده می‌کند؛ در استقرار چندنمونه‌ای، برای محدودیت rate limit سراسری به storage مشترک نیاز است.
- ارسال SMS به موجودی پنل، مجوز وب‌سرویس، خط فرستنده و محدودیت‌های اپراتور وابسته است. ارسال واقعی باید پس از ثبت Secretها و با شماره‌ی آزمایشی مجاز بررسی شود.
- برای پرداخت واقعی، `NEXT_PUBLIC_SITE_URL`، Merchant ID، حالت Sandbox/Live و callback دامنه باید قبل از استفاده نهایی بازبینی شوند.
- هنگام افزودن کنترل یا بخش جدید، breakpointها و کلاس‌های responsive موجود را حفظ و نتیجه را در عرض موبایل و دسکتاپ بررسی کنید.
